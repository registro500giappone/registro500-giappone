# 壁紙ジェネレータ HANDOFF（正本）

> **これは何か**：登録されたメイン写真から、オーナーが自分で待ち受け画像を作れる機能。
> 第一弾は**オールタイル図鑑**＝全登録車を敷き詰め、ログイン済オーナーだけが自分の1台をハイライトできる。
> **現在地：段1（絵の設計）完了・段2（画面の実装）は骨格が動いた。残りは実機での確認。**

## §2 並び順のロジック（正本）

### 2-1 色順は「案3」で確定

```
白 → クリーム → グレー → 黄 → 橙 → 赤 → 紫 → 紺 → 青 → 水色 → 緑 → 黄緑
```

- ⛔**案2（グレーを黄の後）は不採用**＝水色と青が離れるため（ユーザー判断）。
- ⭐**グレーはクリームの隣**＝橙の後に置くと「余り物・色不明」に見えるという指摘から。

### 2-2 グループ内は濃淡＋1つおき反転

- **申告された `body_color` が主**。66種の自由記述を辞書で13グループへ正規化（156台）。
  - 「→」は後ろを採用、「／」「/」「・」は先頭を採用。
- **空欄13台だけ写真から推定**（中央帯を quantize して最大クラスタの色相で判定）。
- ⚠️**濃淡は写真の平均色では測れない**（空・アスファルト・紅葉・建物を拾う）。
  **申告グループの色相域に該当する画素だけ**を抽出して `L = V*(1-S/2)` の平均を取る。
- ⭐**1グループおきに向きを反転**（淡→濃／濃→淡）＝境目が必ず「濃と濃」「淡と淡」で接し、169台がひと続きのグラデーションになる。
  - 実測の向き：白45↓ / クリーム16↑ / グレー11↓ / 黄31↑ / 橙4↓ / 赤11↑ / 紫1↓ / 紺13↑ / 青7↓ / 水色20↑ / 緑5↓ / 黄緑5↑

### 2-3 ロゴを両端に置く理由

⭐**この置き方は色順の設計があって初めて成立する。** 並びが白から始まるので、白地の500ロゴが先頭で白い車の列に紛れる。
2枚を並べると「明るいタイル2つの塊」になり、末尾だと**余った枠の埋め合わせ**に見えた。両端へ離すとその両方が消える。
本の表紙と奥付の構造で、169台のうち126は6台という実態とも順番が合う。

⚠️**唯一の弱点＝126と500が離れるので、2つのロゴを対にして見せる用途には向かない。**その必要が出たら末尾に2枚まとめる案（L5）へ戻す。

## §4 実データから出た分岐（⭕2026-09-04 ユーザー決定済・段2で実装する）

DB実測（2026-09-04・総170台／オーナー紐付け116台／113ユーザー）：

1. **2台以上を登録しているオーナーが3人**（いずれも2台）
   → ⭕**どちらをハイライトするか選ばせる**（決定）。2つ置くと2×2が2箇所になり「自分の1台」の意味が崩れる。
2. **自分の車が図鑑に載っていないオーナーが1人**（`sns_share_optout` のため）
   → ⭕**黙って失敗させず理由を出す**（決定）。「SNS掲載をオフにしているため図鑑に載っていません」＋設定への導線。写真未登録の車は現時点0台だが同じ扱い。
3. **端末ごとの画面サイズ**
   → ⭕**見ている端末の実サイズで作る**（決定）。1179×2556 は iPhone Pro 系の一例にすぎず、固定値ではない。
   台数から列数を選ぶ仕組みなので画面が変われば格子も追随する。⛔代表サイズから選ばせる案は不採用。

## §6 不変条件・技術上の罠（⛔踏まない）

- ⭐**スプライトシート方式が CORS を回避している。** 169台を1枚のWebPに焼いて**自ドメインから配信**するので canvas が汚染されない。
  ⚠️**Firebase Storage には CORS が設定されていない**（`Access-Control-Allow-Origin` なし）＝ブラウザから直接読むと canvas が汚染され `toBlob`/`toDataURL` が SecurityError で落ちる。**第二弾で元写真を直接使うなら、先に CORS 設定かプロキシが要る。**
- ⚠️**メイン写真は長辺1000px**（`edit.html:829` の cropper で 1000×1000 にクロップされる）。1枚デカ使いは破綻するが、タイルなら余裕。
- ⚠️**iOS Safari の canvas 総ピクセル上限は約16.7Mpx。** 現行スプライトは 3328×3328 = 11.1Mpx で収まっているが、台数が増えると超える。
- ⚠️**iOS Safari は `<a download>` が効かない**＝保存は長押しの導線が要る。
- ⛔**スプライトに入れるのは `sns_share_optout` でない車だけ**（掟＝ `MEMORY_watchlist.md` 冒頭）。
- ⚠️**横倒しの写真が3台**（DOC_47・DOC_96・DOC_98）＝いずれも時計回り90度で正しくなる。EXIF の回転情報が失われて横長のまま保存されている。
  補正表＝`wallpaper/proto/rotate-fix.json`。⚠️**元写真そのものが傾いているので、車両ページでも横倒しに表示されているはず**＝根本の直し方は別の判断（撮り直し／管理画面で回転を保存／表示側で自動判定）。
  全169台をエッジ量で走査済みなので**他に同じものはない**（DOC_12 は真上からの俯瞰写真で向きは正しい）。
- ⛔**導線（メニュー・リンク）は付けない。** ユーザーの明示指示があるまで（CLAUDE.md の掟）。

## §7 試作の在り処と再現手順

> ⚠️**段2の実装が済んだので、本番はこの試作ではなく `py/build_wallpaper_sprite.py`（§8）。**
> proto/ は**絵の検討に使った版**として残す（見本JPEGを作り直したいときだけ使う）。
> ⛔色順のロジックを直すときは本番側を直す＝proto/ を直しても本番は変わらない。

```
wallpaper/proto/
  build_sprite.py   Supabase REST(公開キー) → Firebase並列DL(ローカルキャッシュ) → 256px角 → 13列スプライト
  make_phone.py     色の正規化・濃淡測定・並び順・レイアウト・見本生成（段2の移植元はここ）
  make_page.py      検版ページ（Artifact用HTML）の生成
  rotate-fix.json   横倒し写真の補正表
```

- 実行は `wallpaper/proto/` で `python build_sprite.py` → `python make_phone.py`。
  `cache/` にDL済み写真、`out/` にスプライトと manifest、`out/phone/` に見本が出る（いずれも gitignore 済み）。
  ⚠️別の場所へコピーして走らせるなら、ロゴ画像を探すために環境変数 `R500_ROOT` に repo ルートを渡す。
- 生成物：`sprite-v1.webp`(2.33MB) / `manifest-v1.json`(17.3KB) / 見本JPEG群。
- 原寸の見本JPEGは公開repo外の `registro500-notes\wallpaper-mock\phone\` にコピー済み。

### 8-2 段2で決めたこと（⛔勝手に戻さない）

- ⭐**色順の並びは Python 側で確定して manifest に焼き込む。** 色グループの辞書（66種の自由記述）と
  濃淡の測定は画素を見る処理で、ブラウザへ移植すると**必ず二重管理になってズレる**。
  ブラウザは `order_color` を読むだけ。⛔ JS 側に色の辞書を持たせない。
- ⭐**焼き直しの引き金は「署名」**＝`document_id + 写真URL + body_color + updated_at` の SHA256。
  新規登録・削除・写真の差し替え・SNS掲載設定の変更・色の書き換えのどれでも変わる。
  変化が無い日は何も書かない＝**毎日流してもコミットは増えない**（連載公開ワークフローと同じ考え）。
- ⚠️**写真キャッシュの名前に写真URLと更新日時を混ぜてある**（`<doc>-<hash>.jpg`）。
  `document_id` だけで名付けると、**オーナーが写真を差し替えても古い1枚を使い続ける**。
- ⭐**ページ名は `my-wallpaper.html`（`/my-wallpaper`）。**⚠️`wallpaper.html` にしなかったのは、
  Cloudflare Pages が拡張子なしURLへ寄せる一方で **`wallpaper/` というディレクトリが実在する**ため
  （`/wallpaper` の行き先が曖昧になる）。⛔このURLは変えない。
- ⚠️**スプライトは `sprite.webp?v=<署名の先頭8桁>` として読む。** Service Worker が画像を
  CacheFirst で抱えるので（`sw.js:109`）、URLが変わらないと**焼き直しても古い1枚が出続ける**。
  `manifest.json` は SW 側が NetworkFirst なので素通しでよい（`sw.js:103`）。
- **判定不能のときはハイライトを出さない。**⚠️連載の門番は「読めるはずの人が読めない」を避けて
  緩める側へ倒すが、ここは**逆に倒す**＝取り違えると他人の車を「あなたの1台」として大きく出すことになる。
- ⭐**登録済オーナーは「未ログインのまま来る」ほうが多い**（170台のうち紐づけ済みは116台）。
  その人が詰まらないよう**入口を3つ**置く＝①操作の並びの中の「ログインして大きくする」
  ②案内カードの「このページでログインする」③「マイガレージでログインしてから戻る」。
  ⚠️**案内カードだけでは足りない**＝縦長のプレビューに押し下げられて画面の外に出る。
- ⭐⭐**ログイン状態を上部に常時出す**（未ログイン＝「ログイン」／ログイン中＝アドレスの一部＋「切替」）。
  ⚠️**2026-09-04 の実機で踏んだ**＝ログイン済みのまま「このアカウントには車両の登録がありません」だけが出て、
  **ログインの入口がどこにも無い**画面になった。**状態が見えないと、詰まったときに打つ手が無くなる。**
- ⭐**車が見つからないときは、いま入っているアドレスを本文に出す。** RLS も列権限も SELECT を許して
  いる（`cars_select_policy` は `qual: true`・6列とも anon/authenticated に GRANT 済＝2026-09-04 実測）ので、
  0件の最頻の理由は**登録と違うアドレスでログインしていること**。「別のアドレスでログインし直す」を必ず添える。
- ⛔**照会が失敗したときに黙らない。** 何も出さないと、読み手には「壊れている」としか映らない。
- ⭐**保存の案内は画像の真下に出し、画像ごと画面へ引き戻す**（`scrollIntoView`）。
  ⚠️**文言は実機のメニューのまま書く**＝長押しで出るのは「**“写真” に保存**」
  （2026-09-04 実機で確認。当初「“写真”に追加」と書いていて指摘を受けた）。
  近い言い換えにすると、読み手はメニューの中で探し物をすることになる。
  ⚠️保存ボタンは画面のずっと下にあるので、押した場所に案内を置くと**長押しすべき画像が視界の外**に残る。
- **戻り先を必ず出す**＝上部に「← マイガレージへ戻る」（`/edit?type=500`）。
  この画面は**他から来て・作って・帰る**場所で、⛔行き止まりにしない。
- 検証用のパラメータは**2つに分けてある**。`?preview=1`＝**PCでも組む**
  （⭐ログインの判定は本物のまま＝**未ログインの見え方をPCで確かめられる**）／
  `?hi=12`＝その番号の1台を仮ハイライト（絵の確認用）／`?ios=1`＝**iPhone扱いにする**
  （長押し保存の案内をPCで確かめる）。⛔本番の導線には出さない。
