## 2. 確定した設計判断（ユーザー承認済み）

### 2-1. イベントは分類しない ← 重要
当初「みんなで行く／情報として知る」の2分類を提案したが、**ユーザーが却下**。
理由は「イベントの性質はグラデーションで、分けられない」。

代わりに **反応が濃淡を作る** 設計にする。

- 全イベントに **✅参加します**（宣言・名前が出る）と **👀気になる**（メモ・人数のみ）を並べる
- 種別設定は持たない。表示が反応量で自動的に変わる
  - 参加3人以上 → 顔ぶれを主役に
  - 参加1〜2人 → 控えめに
  - 参加0・気になる有 → **「◯人が気にしています」**（最初の1人を出しやすくする）
  - 両方0 → 情報カードとして淡々と
- 「気になる」が溜まったらその人たちへ「他に◯人が気にしています」と通知

### 2-2. SNSからの自動収集は行わない
X / Instagram / Facebook はいずれも外部からの検索収集を設計上ふさいでいる
（API有料・上位プラン限定・事業者審査必須、規約上スクレイピング不可）。
**機械にSNSを巡回させる案は破棄**。代わりに §2-3。

### 2-3. 情報収集は「人の目＋機械の入力代行」
- **採用**: 「見かけたら貼るだけ」投稿（URL/テキストを貼る→AIが日付・場所・名前を抽出→下書き→管理者が承認）
- **採用**: ウェブ検索での月次探索（公式サイト・ブログ・自治体観光ページ。SNS以外は機械で拾える）
- **却下**: 年次リピートの自動下書き。ユーザー判断「名前や時期が変わることがあり、
  予備情報がないのに自動で出すのはミスリードになる」
  - ただし **サイトには何も出さず、管理者に思い出させるだけの私信** なら可（第5段階で再相談）
- **同じ理由で「昨年の同時期のイベントを表示」も却下扱いに変更**。
  訪問者が「今年もある」と誤解する。**「2025年の記録」と明示したアーカイブとしてのみ**出す

### 2-4. 投稿のハードルを下げる（論点A）
ユーザーの意思：「私では全国を網羅できない。**地域のローカルなイベントもここに載せてほしい**」。
→ 「管理者が引き受ける前提で自動化」案は**撤回**。投稿しやすさを主要施策に格上げ。
→ ただし **公開前の承認は必ず残す**（誤情報は人を無駄足させるため）。

### 2-5. 参加表明の実名表示は現状維持（論点B）
ユーザー「正直わからない。現状に特に抵抗はなさそう」→ いじらない。
新設する「気になる」だけ人数のみ表示にして、ハードルの差を作る。

## 4. 第1段階の実装内容（完了・未公開）

### 成果物
| ファイル | 役割 |
|---|---|
| `py/gen_event_pages.py` | `events/<slug>/index.html` を生成（35件） |
| `.github/workflows/event-pages.yml` | 6時間おき（`20 */6 * * *`）＋手動実行 |
| `event-slugs.json` | URL対応表。**一度決めたslugは変更しない** |
| `events/<slug>/index.html` | 生成物35件（コミット済み） |

### URL形式
```
/events/2026-nikitou-meeting-7/
```
- **`/event/...` は使わない**。`event.html` が `/event` を占めており、フォルダを足すと
  どちらを指すか曖昧になる。プレビュー環境が無く安全に試せないため、
  月102クリックの `/event` を実験台にしない判断（→ `events` 複数形で衝突を回避）
- 年を頭に付ける理由：翌年の同名イベントと衝突しない／「◯◯ 2026」という実際の検索語に一致
- カタカナは音のままローマ字化（`nikitou-meeting`）。`LOANWORDS` 辞書で主要な外来語だけ英語に寄せている
- **英字が気に入らない場合は `event-slugs.json` を手で直す**。公開後の変更はリンクが切れるので公開前に

### なぜ静的生成か
LINE・X・Facebook の共有カードを作るクローラーは **JavaScriptを実行しない**。
既存の `detail.html` / `video.html` はJSで中身を書くため、共有してもサイト名しか出ない
（**この問題は動画ページ・車両ページに現存する。第4段階以降で要対応**）。
骨格を本物のHTMLで書き出すことでOGPとJSON-LDが確実に届く。
参加表明だけは焼き付けると古くなるため表示時に取得する**ハイブリッド**。

### 日付の扱い（絶対に壊さない）
`event.html` は日付を `YYYY-MM-DDT00:00:00+09:00` で保存 → DBにはUTCで入る。
**UTCの日付部分をそのまま使うと1日ずれる**（ニキトウミーティング７は10/3ではなく10/4）。
必ずJSTへ直してから日付を取る。**JSTで00:00ちょうどは「開催時刻の入力なし」**という
保存側の規約（`event.html` の時間判定ロジックと同じ）。その場合 `startDate` は日付のみで出す。

### 構造化データで推測で埋めないもの
| 項目 | 理由 |
|---|---|
| `organizer` | 外部主催が多く不明。Registro500名義で出すと事実と異なる |
| `offers` | 費用が自由記述（「カンパ制」等）で価格を確実に取れない |
| `image` | イベントごとの写真をまだ持たない（第4段階で写真が付いたら追加） |

### 検証済み（35件全件）
JSON-LD必須項目／canonicalとurlの一致／OGP4種／曜日の検算／表示日付とJSON-LDの整合。
実データを差し込んだブラウザ描画で、参加者あり・なし両方の表示を確認。

## 7. 不変条件（壊さないこと）

1. **イベントを種別で分類しない**。反応の量で見え方が変わる設計（§2-1）
2. **予備情報のない自動下書きを作らない**。機械は「探す」「入力を代行する」まで。**公開の判断は必ず人間**
3. **日付はJSTへ直してから使う。JST 00:00 は時刻未入力**（§4）
4. **構造化データを推測で埋めない**（§4）
5. **一度決めた slug を変えない**（リンクが切れる）
6. **導線を勝手に付けない**（CLAUDE.md の全体規約。§5の手順を守る）
7. **`/event` を実験台にしない**。サイトの検索流入の54%を稼ぐ最重要ページ
