# # Registro500 Giappone

クラシック Fiat 500（110D / 110F / 126 系）オーナー向け
**完全無料・永続運用可能な登録 & 公開プラットフォーム**

# 🎯 プロジェクト目的

* 日本国内のクラシック Fiat 500（110D / 110F / 126 系）個体を登録・蓄積し、
  オーナー／オーナー候補が情報共有できるオンラインガレージを作る。
* 一般ユーザーは **一覧・詳細** を自由閲覧。
* 登録・編集は **オーナー本人のみ**（メール認証に基づく）。
* 完全無料の運用を前提とし、長期安定性を最優先とする。

# 🔐 **認証・権限まわり（保存版｜2025-11-23）**

> 今後、新しいチャットを開始するときは
> **必ずこのセクションを AI に読ませること。**
> 過去に“認証方針の巻き戻り”が発生したため。

## 🎯 結論（現時点の最適で安定する構成）

### ✔ 1. **書き込み権限の最終判定は GAS 側（OwnerEmail 照合）**

* 保存処理 `saveCarFromForm()` 内で
  **OwnerEmail と実際のユーザーを照合**し、不一致なら書き込み拒否
* このレイヤが最も安定しており、プロジェクトの根幹

### ✔ 2. **Firebase Auth は owner.html（スマホ導線）専用に限定**

* スマホのログイン体験は Firebase Auth（実運用で正常）
* “マイ車両一覧” と “新規登録導線” はここで成立する

### ✔ 3. **PCの editGate（owner_edit_gate.html）では Firebase を使わない**

* PC では Firebase Auth の Googleログイン直後に
  **edit.html へ遷移すると Apps Script が 403 / 真っ白画面**になる
* 原因は「ログイン直後の一発目の GET だけ認証が不安定になる」Google 側のクセ
* よって PC 用の editGate は：

  * **案内ページのみ**
  * 「編集画面へ進む」ボタンで **素の GET** による遷移
* 認証・権限は保存時に GAS が最終判断するため問題なし

### ✔ 4. **最終的な理想は Firebase Auth 一本化だが、“現段階ではやらない”**

理由：

* GAS WebApp × Firebase Auth の併用は PC で 403 を誘発する
* 安定運用を最優先し、**ハイブリッド構成が実証的に最良**

## 🧪 この結論に至った検証経緯（重要）

1. Firebase Auth を detail → editGate → edit に組み込んで検証
2. スマホは成功
3. PC（複数Googleアカウント環境のみ）で
   **ログイン直後の /edit リクエストが必ず403になる**ことを確認
4. 自動遷移 → 失敗
5. 手動遷移 → 一部成功だが不安定

# 🏗 アーキテクチャ変更の記録 (2025-11-23)

## 1. 背景と当初の構成
**プロジェクト:** Registro500 Giappone  
**目的:** Fiat 500 個体のオンラインガレージ（登録・共有サイト）の構築。  
**要件:** 完全無料、スプレッドシートでのデータ管理、Googleアカウント認証。

**当初の構成 (GAS WebApp Monolithic):**
* **Frontend:** GAS (`HtmlService`) が HTML を生成して配信。
* **Backend:** GAS がスプレッドシートを読み書き。
* **Auth:** Firebase Auth と GAS のセッション (`Session.getActiveUser`) のハイブリッド。

## 2. 直面した課題 (The "GAS Wall")
開発を進める中で、**GAS WebApp 特有の仕様**により、解決困難な問題が多発した。

1.  **403 エラー (複数アカウント問題):**
    * ユーザーがブラウザで複数の Google アカウントにログインしている場合、GAS WebApp へのアクセス権限が正しく判定されず、不定期に `403 Forbidden` エラーが発生する。
    * これはプラットフォーム側の仕様であり、コード修正では回避不可能。
2.  **デプロイの反映ラグとバージョン管理:**
    * コードを修正しても、「デプロイを管理 -> 新しいバージョンを作成」の手順を踏まないと Web 上に反映されない。
    * この手順ミスや、ブラウザキャッシュの強力さにより、「修正したはずなのに画面が変わらない」現象が頻発し、開発効率が著しく低下した。
3.  **画面遷移と認証の相性:**
    * Firebase Auth でログインした後、GAS のページにリダイレクトや遷移を行うと、セッションが途切れやすく、ユーザー体験（UX）を損なう挙動となった。

## 3. 解決策の検討
これらの問題を根本解決するため、いくつかの代替案を比較検討した。

* **案A: FlutterFlow / Softr**
    * メリット: 開発が早い。
    * デメリット: 既存の HTML/CSS 資産をすべて捨てる必要がある。無料枠の制限や、スプレッドシート連携の柔軟性に懸念がある。
* **案B: Firebase Hosting + Firestore**
    * メリット: 高速・安定。
    * デメリット: スプレッドシートが使えなくなる。データ管理画面を自作する必要があり、運用コストが高い。
* **案C: 分離型 (Headless Architecture) - Vercel + GAS API [採用]**
    * **Frontend:** Vercel (静的ホスティング) に HTML/CSS/JS を配置。
    * **Backend:** GAS を「JSON を返すだけの API」として稼働。
    * **Database:** Google Sheets (そのまま維持)。

## 4. 新アーキテクチャのメリット
この「分離型」を採用することで、以下の解決を図る。

1.  **403 エラーの根絶:**
    * Web サイト自体は Vercel (Google 以外のサーバー) に置くため、Google アカウントのログイン状態に依存せず、誰でも閲覧可能になる。
2.  **デプロイ問題の解消:**
    * Frontend の修正は Vercel にアップするだけで即時反映される。
3.  **資産の有効活用:**
    * これまで作成した HTML/CSS デザインや、GAS のデータ処理ロジック (`saveCarFromForm` 等) を 90% 流用できる。
4.  **標準的な Web 技術への回帰:**
    * GAS 特有のブラックボックスな挙動に悩まされず、一般的な `fetch` 通信と CORS 設定のみで制御可能になる。
