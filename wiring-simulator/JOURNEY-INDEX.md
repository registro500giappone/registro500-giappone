## §1 「漏れなく」をどう担保したか

思いつきで症状を並べると必ず漏れる。ここでは**原典そのものを軸にした**。

- 原典 500D 取説 p40 の凡例は **35部品**（`registro500-notes\wiring-work\d_netlist.md` に全結線を転記済み・F型は16系統すべて結線同一を確認済み）。
- 配線図ビューアの系統分けは **16ページ＝全表示＋15系統**（`wiring-preview.html` の `LAB`）。
- **35部品が最低1つの旅に登場するか**を §3 の表で数えた＝これが漏れの検証。**現在の目次で35部品すべてを覆えている**。
- 覆えないもの＝**L1（到達性）では原理的に表せない症状**は §4 に理由付きで隔離した。「まだ作っていない」と「作れない」を混ぜない。

⚠️**系統番号 = ビューアのページ番号 = `wiring-net.json` の `sys`**（3つは同じ番号体系）。部品番号（1〜35）は原典凡例の番号で、別物。

## §4 旅にできないもの（作らない・理由付き）

⛔**「まだ作っていない」ではなく「L1では作れない」**。ここを旅にすると、絵の上では「つながっている」と出るのに実車では直らない＝**診断の道具として人を誤らせる**。第3号の `limitations` で顕在化した話と同じ。

| 症状 | できない理由 | 担当 |
|---|---|---|
| セルが**力なく**回る／ヘッドライトが**暗い** | L1 は電気の「細さ」（抵抗・電圧降下）を持たない。実車で最頻の原因がこれ | **UCM-1**（クランキング電圧・区間電圧差） |
| 駐車中に**バッテリーが上がる**（暗電流） | 電流量の話。到達性では「常時電源に何かが繋がっている」までしか言えない | UCM-1／実測 |
| **時々**点かない・振動で消える（接触不良） | 断続の時間軸を持たない | 実車の作業 |
| 点火時期がずれる／ドエル角が開く | 電気の道は正常なまま値だけが動く | ⭐**UCM-1 の本領** |
| 過充電で**球が切れる** | 電圧の大小を持たない | UCM-1（`charge_v_overvoltage`） |
| ウインカーの**点滅が速い**（球切れ時） | 熱式フラッシャーの動作は消費電流依存 | ⚠️#15 では「片側が点かない」までを扱い、**速さは文章で説明する** |
| 配線が焼ける・煙が出る | 電流量。ただし**短絡の検出（`shorted`）は持っている**ので「そうなる条件」は言える | 注意喚起として本文へ |

⚠️**この表は #11・#15 を作るときに必ず読む**。点火系とウインカーは「電気の道は正しいのに症状が出る」領域と隣り合っていて、境界を書かないと嘘になる。

## §5 実装順の提案（根拠付き）

### 第1群：データ追加ゼロで書ける（いま持っている札だけ）

- **#4 キーを回しても何も点かない** … `battery`／`f1`／`ign_sw`／`quadro` の既存4部品で全場面が解ける見込み。**第3号と対になる**（#3＝「灯は点くのにセルが回らない」／#4＝「灯も点かない」）＝第3号の絵が既にこの上下分割を描いてある。
- **#5 アース／マイナス** … **案A（アース基準をバッテリー `-` へ移す・`wiring-sim.js` 3行）の実装が前提**。逆に言えば**案Aを入れると #5 が旅として成立する**＝修正の動機がここに直結する（HANDOFF §0 その4）。

### 第2群：小コスト（第2号の「センダ→灯」型の反復）

- **#6 燃料** … 部品追加は実質1つ（センダ5＋`quadro` に灯16）。構造は第2号と同型。**ただし R型は燃料計＝型式差の初実装**になる。
- **#7 ホーン**・**#8 ルームランプ** … どちらも**F1の負荷側**にぶら下がる。⭐**SCHEMA §G 持ち越し3（ヒューズ負荷側の端子名が原典に無い＝合成端子 `_out`）を決着させるのはこの2本**。
- **#9 ブレーキ** … ヒューズ 15/54（キーON側）の初実装。#4 と組み合わせると「キーONで何が生きるか」が言える。

### 第3群：新しい構造（ここから学びが増える）

- **#11 点火系** … ⭐**UCM-1 との接続が最も濃い**（ドエル角4枚・`static_strobe_advance_gap` 等が全部この部品の話）。**高圧側（コイル二次〜プラグ）をL1でどう扱うかの設計判断が要る**＝一次側の輪だけをL1で解き、二次は「一次が切れれば火花は出ない」と文章で繋ぐ形が素直。
- **#10 メーター照明** … ⭐**SCHEMA §G 持ち越し2（計器盤 `30` の給電元が原典で割れている）の期限**。#1・#2 の灯が採用している `INTER` の推定を、ここで原典から決着させる。

### 第4群：大物（型式差が本番）

- **#13 ヘッドライト** … ⭐**SCHEMA §G 持ち越し1（イグニッションSW `30/4`×2 の内部接点）の期限**。「キーを抜いても外部灯が点く」の理由がここ。
- **#14 スモール・テール**・**#15 ウインカー**・**#12 ワイパー** … 部品数が多い。**#12 と #15 は F/L/R で図そのものが違う3系統**（残り13系統は1本も違わない＝`wiring-preview.html` の記述）。型式分岐の作りが必要。

### 💡順番についての所見

**第1群（#4・#5）はデータを1行も足さずに2本増える**＝いま最も安い。しかも #5 は案Aの実装と一体で、**公開中の第3号本文の「限界②」の記述を消せる**（HANDOFF §0 その4 で「レビューと同時が自然」としてある作業がここで回収される）。

一方 **#11（点火系）は単独で価値が高い**（UCM-1接続・「セルは回るのにかからない」は遭遇頻度が高い・#3 の続きとして物語が繋がる）。安さを取るなら #4→#5、価値を取るなら #11。

## §7 この目次の使い方・注意

- **番号（#4〜#15）は目次上の通し番号であって、公開順でも `journey_id` でもない。** URL と `journey_id` は実装時に症状名から決める（第1〜3号と同じ流儀・一度決めたら変えない）。
- **1つの旅に詰め込まない。** 例えば #14（スモール・テール・ナンバー灯）は3部位を1本に入れているが、実装時に重くなったら分ける。⚠️逆に**#13 と #14 を1本にまとめない**（外部照明SW・コミュテータを共有するが、症状としては別物＝1症状=1ページ=1URL の原則）。
- **⛔導線は付けない**（作業場URLのまま・HANDOFF §6-3）。公開の判断はユーザーが出す。
- **型式差のある旅（#6・#10・#12・#13・#14・#15）は、F型だけ作って「L/Rは後で」としない。** 原典の図が違う以上、間違った図を見せることになる。作るときに型式分岐まで含めて設計する。
- 各旅を実装したら `ucm1-interop/journeys.json` に1件足す（`journey_id`／`limitations`／`measurable_by_ucm1` を必ず書く）。
