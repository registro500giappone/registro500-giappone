# UCM-1 へ渡すもの（registro500 側の受け渡し口）

> **これは「UCM-1 から参照があったときに、そのまま渡せる状態」で置いてある一式。**
> 取り決めの本体は `wiring-simulator/HANDOFF.md` §3「知識層の共同所有」。ここはその実物。
> 2026-08-21 作成（旅ページ第2号の実装に合わせて）。

---

## 1. 何を渡して、何を渡さないか

正本は3つに分かれている（§3 の決定）。**この repo が持っているのは左の1列だけ**で、渡すのもそれだけ。

| registro500（この repo） | UCM-1（`Documents\ucm1`） | cars DB |
|---|---|---|
| 結線・実配置・**到達性**（どこが電源／アース／点く・点かない） | **測定値・しきい値・判定・診断カードの文章** | 車両個体の仕様 |

- ✅渡す＝`journeys.json`（旅ページの登録簿。結線の鎖・到達性の解・電気的に区別できない組・実車配置の参照）
- ⛔渡さない＝しきい値や判定文（そもそも持っていない）。UCM-1 側の値を引用したい時は §3 のルールどおり **構造と数値だけ借りて文章は書き下ろす**。

### ⚠️逆向きの禁止事項（こちらが守る側）

**UCM-1 の診断カード本文を公開Webへ転載しない。** 整備書照合で書かれた文章なので権利面の問題がある。使ってよいのは原因リスト・確からしさ・切り分け順といった**構造**と、裏取り済みの**数値**まで。旅ページの文章は全部こちらで書き下ろしている。

## 3. IDの扱い【2026-08-21 決定】＝対応付けるが、同一視しない

**旅ページのID（`journey_id`）と UCM-1 の `trigger_id` は別物として持つ。**

| | 誰のもの | 変わるか |
|---|---|---|
| `journey_id` | registro500 | **不変**。URL と対＝一度決めたら変えない（`event-slugs.json` と同じ扱い） |
| `ucm1_trigger_id` | UCM-1 | **変わりうる**。対応表の1列にすぎない |

### なぜ分けたか（2026-08-21 に ucm1 を実読して分かった3点）

1. **UCM-1 の `trigger_id` 13件は全て仮命名**で、Phase 3 でアプリ側の判定ロジックの命名へ突合される（突合方向＝ucm1 JSON側をアプリ側に合わせる）。**相手側のIDは確実に動く。**
2. **`charge_lamp_on` 自体が改名候補**。v2.34 決裁で VOLT-04 の意味論が「チャージランプ点灯」→**「充電喪失」**へ一般化されており、突合時の改名が検討対象になっている。
3. **guide カードに `trigger_id` は付けられない**。スキーマ 1.1 の規則で `card_type=diagnostic` のとき必須・`guide` のとき省略。実データも例外ゼロ（OILTEMP-01・**OILPRESS-01**・START-01・START-02 の4枚は全て `None`）。

### `starter_no_crank`（旅ページ第3号）の扱い

**UCM-1 側にいま足すものは無い**（`oil_lamp_on` と同じ理由）。同題材は **START-02「セルが回らない」**だが guide カードなので `trigger_id` を持てない（上記3）。始動系の diagnostic が載る時点で突合する。

⚠️**この旅は UCM-1 にとって一番おいしい**：原因の中で実車で最頻の「接触抵抗による電圧降下」を、**こちらの L1 到達性は原理的に表せない**（`limitations` に明記した）。**測って初めて割れる領域がはっきり分かれている**＝旅ページ側は「クランキング電圧」「区間ごとの電圧降下」の**測る場所の定義**まで用意し、良否の値は持たない。

### `key_no_power` / `ground_return` / `no_spark`（旅ページ第4〜6号・2026-08-21 追加）の扱い

**3本とも UCM-1 側に対応するカードが無い＝いま足すものは無い。** 相手のIDが決まっていないのではなく、**同題材のカードがそもそも存在しない**（`ucm1_trigger_id.card` は `null`）。

- ⭐**`no_spark` は将来の本命**＝UCM-1 の**ドエル角カード4枚と直結する**題材。ただし**ドエル角も点火時期も「角度と時間」の話で、こちらの L1 到達性は原理的に表せない**（`limitations` に明記）。旅ページ側は「コイル＋とコイルDの2点測定」までを定義し、**ドエル角・進角は測定側の担当**として最初から手放してある＝役割の境界がいちばんきれいに割れている旅。
- ⭐**`ground_return` も測定向き**＝アース不良の実車での典型は「完全に外れる」ではなく「錆びて細くなる」で、これは L1 では表せない。**バッテリー −端子と車体の電圧差／セルを回している間のエンジン↔車体の電圧差**という測る2点の定義を用意した。
- **`key_no_power` は第3号（`starter_no_crank`）と対**＝「灯は点くのにセルが回らない」／「灯が2つとも点かない」で、同じ分岐点を逆から見ている。UCM-1 に VOLT 系の diagnostic が増えたときに突合する。

⚠️**系統9（点火）は一次側だけ**を持ち、**二次側（高圧）とコンデンサは持たない**。「つながっている＝火花が出る」と誤読させないための設計判断で、`no_spark` の `limitations` と `wiring-net.json` の `_sys9_scope` に理由を書いてある。**UCM-1 側の文章でもこの境界を越えないこと。**

### `horn_silent` / `room_lamp_dark` / `brake_no_light`（旅ページ第7〜9号・2026-08-22 追加）の扱い

**3本とも UCM-1 側に対応するカードが無い＝いま足すものは無い**（ホーン・室内灯・ブレーキ灯は計測対象ではない）。ただし**キーとの関係が系統ごとに逆になる**ので、判定文を書くときの前提として渡しておきたい。

- ⚠️**`horn_silent` / `room_lamp_dark` はスイッチが【アース側】に入る**＝ボタンは電気を送るのでなく帰り道をつなぐ。副作用として**キーの位置と一切無関係に働く**（鍵を抜いてもホーンが鳴るのが正常）。**UCM-1 の「キーONで測る」前提とは違う。**
- ⚠️**`brake_no_light` は逆にキーON側**（ヒューズ F2＝15/54）＝UCM-1 の前提とちょうど合う。⭐ただし**F2 が切れても点火と警告灯は生きる**（コイル + と計器盤 INTER への線は**ヒューズの手前**で分かれる）＝**「エンジンがかかる＝ヒューズは無事」と書かないこと。**
- ⚠️**まだ registro500 側に無いもの**＝F2 の相棒であるウインカー（#15）とワイパー（#12）。原典上は同じ F2 にぶら下がるが netlist に未投入なので、**「ブレーキ灯とウインカーが同時に死んだら F2」はこちらの JSON では再現しない**（`limitations` に明記）。#12・#15 の実装で解消する。
- **測る点の定義だけ置いた**（良否の値は持たない）＝「押した瞬間の電圧降下」（#7）／「駐車中の暗電流」（#8）／「踏んだ瞬間の電圧の落ち込み」（#9）。⛔**UCM のフェーズを前倒ししない。**

### `oil_lamp_on`（旅ページ第2号）の扱い

**UCM-1 側にいま足すものは無い。**

- OILPRESS-01 に `trigger_id` を後付けするのは**スキーマ違反**（上記3）
- 油圧灯の diagnostic カードを新設するには**警告灯タップ**（VOLT-04 と同じ）と metric・test_mode が要る＝**UCM のフェーズ前倒し**になる。それは §3 でしないと決めている
- したがって `oil_lamp_on` は**こちら側の `journey_id` として確定**し、**UCM-1 に油圧灯タップが載る時点で突合**する

### 🙏UCM-1 側にお願いしたいのは1行だけ

`trigger_id` 突合TODO（HANDOFF の13件のリスト）に、

> registro500 の旅ページがこのIDを参照している＝**改名するときは連絡が要る**

と足しておいてほしい。**急ぎではない**（次に ucm1 を開いたときで間に合う）。改名されたらこちらは `journeys.json` の `ucm1_trigger_id` 欄だけ直す＝**URLは変えないので誰のリンクも切れない**。

### あわせて渡しておく実務的な情報（油圧の旅で分かったこと）

**「本当に油圧が低い／センダの固着／GRIGIO線の地絡」は電気的に完全に同じ状態になる。** どれも `quadro.0` がアースに落ちているだけで、L1 到達性でも実車の電圧測定でも区別できない。

- UCM-1 が測って**言えること**＝センダの接点が閉じているか開いているか（GRIGIO 線の対アース電圧。閉≒0V／開はランプ越しにほぼバッテリー電圧＝ソルバーの `post` 状態）
- **言えないこと**＝閉じている理由。ここから先は**油圧計での実測（機械の話）**

旅ページもこの境界をそのまま書いて手放している。**UCM-1 側で油圧灯の判定を作るときも、電気の測定だけで「油圧低下」と断定しない**のが安全側。

## 4. 使うときの注意（`v` を見ること）

`wiring-net.json` の各要素には検証レベルが付いている。**`inf` を断定に使わない。**

| レベル | 意味 |
|---|---|
| `orig` | 原典（大塚氏の配線図）で確認済み＝事実として使ってよい |
| `auto` | 機械的に抽出しただけ |
| `inf` | 推定 |

油圧の旅で `inf` なのは2つ：

- **`quadro.warn_oil` / `quadro.warn_charge` の給電レール側**（`INTER` を採った理由＝キーOFFで点きっぱなしにならないから。計器盤の内部結線は原典の図から読み切れていない）
- **`oil_sender` の接点の向き**（原典は記号だけ。ただし「圧ゼロで閉じる」は油圧警告灯が成立する唯一の向き）

このほか `ign_sw` の内部接点も `inf`（`SCHEMA.md` §G）。

## 5. 旅ページを増やしたときの手順（こちら側の作業）

1. `wiring-journey-<症状>.js` と `wiring-journey-<症状>.html` を作る（型＝`/wiring-journey.js`＋`/wiring-journey.css`）
2. **`journey_id` を決める。URLと対＝あとで変えない。** UCM-1 に同題材の diagnostic カードがあればその `trigger_id` と同じ語を選ぶ（読み合わせが楽になる）が、**一致させる義務はない**（§3）
3. `journeys.json` に1件足す（`ucm1_trigger_id` は無ければ `null`・状態を書く）
4. ⛔**公開導線は付けない**（作業場URLのまま・ユーザーの指示があってから）
