## §A 中心の設計判断＝**ノードは部品ではなく端子**

`origin/wiring-viewer` の試作 `wiring/data/f.json` は**部品単位**（49ノード・13エッジ・`{"from":"battery","to":"ignition_sw"}`）。
**この粒度では到達性計算ができない**＝スイッチは「どの位置でどの端子とどの端子が繋がるか」が本体で、部品を1点に潰すと内部が消える。

→ **ノード＝端子（`部品ID.端子名`）**とする。これは HANDOFF §2-7「測定点は部品側の端子に置く」と同じ粒度＝**シミュレーションの単位と測定の単位が一致する**（L3・UCM-01連携がデータ変換なしで乗る）。

さらに好都合なことに、**端子ノードの集合は既に原典照合済みで存在する**＝`wiring-terminals.json`（F52・L39・R54点・DIN名・図座標・台帳付き）。ノード集合を新規に発明しない。

## §B ファイル構成（静的配信・ビルド無し＝HANDOFF §6-7）

| ファイル | 内容 | 大きさ | 版管理 |
|---|---|---|---|
| `wiring-terminals.json`（既存） | 端子の**図座標**。ここが座標の唯一の正本 | 13KB | `TERM_VERSION`（既存） |
| `wiring-net.json`（新規） | **トポロジー**＝parts・wires・部品の内部挙動。座標を持たない | 小 | `NET_VERSION` |
| `wiring-geom-{f,l,r}.json`（新規・後回し） | 線1本ごとのSVGパス | 大 | `GEOM_VERSION` |
| `wiring-patches.json`（新規） | 仕様パッチ＋出典台帳 | 小 | `PATCH_VERSION` |

**トポロジーと幾何を分ける理由**: HANDOFF §5 が「SVGパス化は総工数の過半」と見積もっている。分けておけば**幾何ゼロの状態でL1のロジックを完成・検証できる**。さらに——

> 💡**幾何が無くても動くL1が作れる**: 既存の端子座標に点を打つだけで「いまどの端子が生きているか」は表示できる。線が光る前に**端子が光る**版が成立する。「線は1本あれば役に立つ」の系＝最初の可視化は既存資産だけで届く。

## §C エンティティ定義

### C-1 parts（部品）
```json
{
  "id": "regulator",
  "label": "レギュレータ",
  "kind": "regulator",
  "sys": 11,
  "terms": ["30", "67", "51", "31"],
  "types": "FLRD",
  "model": { "kind": "regulator_dynamo" },
  "src": "terminals_ledger.md 系統11"
}
```
- `terms` は**DIN名の羅列のみ＝座標を持たない**。座標は `wiring-terminals.json` 側から解決する（重複を作らない）。
- `types`: この部品が存在する型式（F/L/R/D）。**型式差をファイル分割ではなくフラグで持つ**＝端子JSONが既にF/L/Rを1ファイルで扱っている流儀に合わせる。

### C-2 wires（配線＝原典。静的）
```json
{ "id":"w11-03", "a":"regulator.51", "b":"dynamo.51", "color":"MARRONE",
  "sys":11, "types":"FLRD", "v":"orig", "src":"f_netlist §11" }
```
- `v`＝照合レベル: `orig`（原典照合済）／`auto`（機械抽出のまま）／`inf`（推定）。
  **`auto` と `inf` を事実として見せない**＝f_netlist は**ウインカー系以外すべて機械抽出**（HANDOFF §5）。この旗が公開前検証の進捗管理そのものになる。
- 色は**OTSUKA原典の色名**（GIALLO/MARRONE…）を持ち、描画RGBは持たない（パレット表は f_netlist にある）。

### C-3 部品の内部挙動（状態で変わる接続）
```json
"model": { "kind":"switch",
  "positions": { "OFF":[], "ON":[["30","15/54"]], "START":[["30","15/54"],["30","50"]] } }
```
- **wires＝常に繋がっている／model＝状態で繋がる**、この2層の和がその瞬間のグラフ。
- 【2026-08-18 v0.2】`model` は共通で `kind` ／ `v`（この内部モデルの照合レベル）／ `default`（初期状態）／ `note`（何をモデル化し何をしていないか）を持つ。**簡易モデルには `v:"inf"` を必ず付ける**＝原典に描かれていない内部接点を事実として見せないため。
- 【同】ランプ等の負荷は配線ではなく**部品の内部要素**として持つ（`model.kind:"lamps"` の `lamps[]`＝`a`/`b` は同一部品の端子名）。wires は原典に線として描かれているものだけに保つ。
- スイッチの接点構成は**端子台帳作業でかなり判明済**（HANDOFF §5）。レギュレータ・フラッシャーは簡易モデルで足りる。

### C-4 L1 到達性の定義（物理演算なし）
- 電源＝`battery.+`／アース＝`31` を持つ端子とボディ。
- **通電 = B+ から到達可能**。**ランプが点く = 一方が B+ に到達 ∧ 他方がアースに到達**。
- これだけ。電流も電圧降下も持たない（HANDOFF §2-5「L4はやらない」）。

### C-5 期待値テーブルは**持たずに導出する**（L3・UCM-01の要）
測定点の期待値は L1 の到達性から自動的に出る：B+到達＝約12V／アースのみ＝0V／孤立＝—。
**authoredで書くのは物理が要る例外だけ**（例: 走行中のオルタB+＝13.8〜14.5V、ダイナモ車は挙動が別）。
→ HANDOFF §3 の「期待値も仕様パッチで書き換わる」が、**パッチでグラフが変われば期待値も自動で変わる**という形で自然に満たされる。表を二重管理しない。

## §D 仕様パッチ

```json
{
  "id": "gen-alt",
  "label": "オルタネーター換装",
  "sys": [11],
  "when": { "generator": "オルタネーター" },
  "ops": [
    { "op":"removePart", "id":"regulator" },
    { "op":"removeWire", "id":["w11-02","w11-03"] },
    { "op":"addPart", "part": { "id":"alternator", "terms":["B+","D+"], "model":{"kind":"alternator"} } },
    { "op":"addWire", "wire": { "a":"alternator.B+", "b":"starter.+", "v":"inf" } }
  ],
  "ledger": "出典: （施工実例の典拠をここに書く。terminals_ledger の流儀）",
  "types": "FLRD"
}
```
- `when` は**DB列の値そのまま**（§DB実勢調査で確定した `generator`/`ignition_type`/`fuel_pump` の実値）＝ HANDOFF §2-3「登録データを自動適用・手数ゼロ」がマッピング表なしで成立。
- **op は5種で足りる**: `removePart`/`addPart`/`removeWire`/`addWire`/`setModel`。自由描画は入れない（HANDOFF §6-1）。
- 該当パッチ無し → **その系統だけ純正表示＋注記**（§2-6）。パッチは系統単位で当たるので、他系統は自分仕様のまま。

## §G 実装状況（2026-08-18・段取り1 完了時点）

### 入っているもの（`wiring-net.json` NET_VERSION 1）

parts 9 = `body` / `battery` / `starter_sw` / `starter` / `regulator` / `dynamo` / `f1` / `ign_sw` / `quadro`、wires 13（w11-01〜11・w10-01〜02）。**すべて `v:"orig"`**＝原典（D型取説p40の目視転記 `d_netlist.md` と、F原典照合済の `terminals_ledger.md`）から読めた結線だけ。f_netlist の機械抽出は補強にしか使っていない。

回路としては **バッテリー＋ → スタータSW節点 →（MARRONE太）→ レギュレータ30 →（ROSSO太）→ F1の30バス → イグニッションSW30** という幹に、レギュレータ51⇔ダイナモ51、レギュレータ51⇔計器盤51（チャージ灯）、各アースがぶら下がる形。

### 内部モデル（`v:"inf"`＝原典に描かれていない＝そう見せない）

- `regulator`: カットアウトリレー（`CHARGE` で 30↔51）だけ。界磁制御はL1に効かないので持たない
- `dynamo`: `STOP` で 51↔− が導通（電機子巻線）。**これがチャージ灯の点灯理由**。`RUN` で切れ、代わりにレギュレータが 30↔51 を閉じて灯が消える＝キー・エンジンの2状態だけで正しい挙動になる
- `quadro`: チャージ灯を `51`↔`INTER` として持つ。**⚠️反対側が未確定**（原典の計器盤は `30`←BIANCO も持ち、`30` は色疑義で転記保留＝台帳の⛔項目）。キーOFFで点きっぱなしにならない方を採った＝**これは推定なので、計器盤の内部を原典で読み切ったときに必ず見直す**

### 持ち越した疑問（系統を足すときに必ず決着させる）

1. **イグニッションSWの `30/4`×2（NERO）の内部接点**。行き先は外部照明SW21と計器盤で決着済（`d_netlist.md` 未決④）だが、SW内部で30と常時繋がっているのかが未照合。500は**キーを抜いても外部灯が点く**のでおそらく常時30系だが、推定でモデルに入れていない。**系統2（ヘッドライト）を書くときが期限**
2. **計器盤 `30` の給電元**（上記チャージ灯の反対側と同じ問題）。`f_netlist` は F2 側（15/54）から来ていると読み、D原典は BIANCO（30系）と書いていて割れている＝**原典の拡大で決着させる**
3. **ヒューズの負荷側の端子名**が原典に無い（合成端子 `_out`）。F1の負荷側はホーンとルームランプ＝系統5/8を書くときに繋ぐ

### 次の一手（段取り2）

L1のBFS。`wires` ＋ その瞬間の `model.positions` の和で無向グラフを作り、`battery.+` からの到達集合と `body.31` からの到達集合を出すだけ。**入力の状態は3つ**（キー OFF/ON・エンジン STOP/RUN・スタータSW OFF/START）。出力は端子ノードの色分け＝`wiring-terminals.json` の `p`+`t` で座標に解決できる端子だけが図の上で光る。

### 段取り1のデータで検算した結果（使い捨てBFS・2026-08-18）

| 状態 | チャージ灯 | B+に到達する端子数 |
|---|---|---|
| キーOFF・エンジン停止 | 消 | 6（常時30系だけ） |
| キーON・エンジン停止 | **点** | 16 |
| キーON・エンジン回転 | 消 | 11 |
| キーOFF・スタータ引き | 消 | 8（スターターが回る） |
| F1切れ・キーON | **点** | 15 |

- **F1が切れてもチャージ灯は点く**＝イグニッションSWの30がヒューズの電源側から分岐しているため。原典どおりの挙動がデータだけで再現された（作り込んだ結果ではない）
- ⚠️**段取り2で決める必要がある1点**: 純粋な到達性だと**負荷（ランプのフィラメント）を通り抜けて向こう側まで「B+到達」になる**（キーON時の16点にはダイナモ51側が含まれる）。「通電している端子」として塗ると、実際には0V付近の端子まで光ってしまう。**負荷を跨いだ先は別の色（後段）にする**などの区別が要る。L4（電圧計算）をやらない方針は変えずに、色の段を分けるだけで足りる見込み。
