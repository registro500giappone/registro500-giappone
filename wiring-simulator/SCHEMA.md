## §A 中心の設計判断＝**ノードは部品ではなく端子**

`origin/wiring-viewer` の試作 `wiring/data/f.json` は**部品単位**（49ノード・13エッジ・`{"from":"battery","to":"ignition_sw"}`）。
**この粒度では到達性計算ができない**＝スイッチは「どの位置でどの端子とどの端子が繋がるか」が本体で、部品を1点に潰すと内部が消える。

→ **ノード＝端子（`部品ID.端子名`）**とする。これは HANDOFF §2-7「測定点は部品側の端子に置く」と同じ粒度＝**シミュレーションの単位と測定の単位が一致する**（L3・UCM-01連携がデータ変換なしで乗る）。

さらに好都合なことに、**端子ノードの集合は既に原典照合済みで存在する**＝`wiring-terminals.json`（F52・L39・R54点・DIN名・図座標・台帳付き）。ノード集合を新規に発明しない。

## §C エンティティ定義

### C-1 parts（部品）
```json
{
  "id": "regulator",
  "label": "レギュレータ",
  "kind": "regulator",
  "sys": 11,
  "terms": ["30", "67", "51", "31"],
  "types": "FLRD",
  "model": { "kind": "regulator_dynamo" },
  "src": "terminals_ledger.md 系統11"
}
```
- `terms` は**DIN名の羅列のみ＝座標を持たない**。座標は `wiring-terminals.json` 側から解決する（重複を作らない）。
- `types`: この部品が存在する型式（F/L/R/D）。**型式差をファイル分割ではなくフラグで持つ**＝端子JSONが既にF/L/Rを1ファイルで扱っている流儀に合わせる。

### C-2 wires（配線＝原典。静的）
```json
{ "id":"w11-03", "a":"regulator.51", "b":"dynamo.51", "color":"MARRONE",
  "sys":11, "types":"FLRD", "v":"orig", "src":"f_netlist §11" }
```
- `v`＝照合レベル: `orig`（原典照合済）／`auto`（機械抽出のまま）／`inf`（推定）。
  **`auto` と `inf` を事実として見せない**＝f_netlist は**ウインカー系以外すべて機械抽出**（HANDOFF §5）。この旗が公開前検証の進捗管理そのものになる。
- 色は**OTSUKA原典の色名**（GIALLO/MARRONE…）を持ち、描画RGBは持たない（パレット表は f_netlist にある）。

### C-3 部品の内部挙動（状態で変わる接続）
```json
"model": { "kind":"switch",
  "positions": { "OFF":[], "ON":[["30","15/54"]], "START":[["30","15/54"],["30","50"]] } }
```
- **wires＝常に繋がっている／model＝状態で繋がる**、この2層の和がその瞬間のグラフ。
- 【2026-08-18 v0.2】`model` は共通で `kind` ／ `v`（この内部モデルの照合レベル）／ `default`（初期状態）／ `note`（何をモデル化し何をしていないか）を持つ。**簡易モデルには `v:"inf"` を必ず付ける**＝原典に描かれていない内部接点を事実として見せないため。
- 【同】ランプ等の負荷は配線ではなく**部品の内部要素**として持つ（`model.kind:"lamps"` の `lamps[]`＝`a`/`b` は同一部品の端子名）。wires は原典に線として描かれているものだけに保つ。
- スイッチの接点構成は**端子台帳作業でかなり判明済**（HANDOFF §5）。レギュレータ・フラッシャーは簡易モデルで足りる。
- 【2026-08-18 v0.3】**画面の操作レバー→部品位置の対応表も `wiring-net.json` が持つ**（`controls`）。「キーを回すと ign_sw が動く」「エンジンが回ると dynamo と regulator が動く」は車の事実であってUIの都合ではない＝JS側に書くと正本が二重になる。`role:"input"`（通常操作）と `role:"fault"`（故障注入＝L2の先取り）を分けてある。**配列の順番＝適用の順番**で、後ろの項目が前を上書きする（故障は入力より後ろに置く）。

### C-4 L1 到達性の定義（物理演算なし）【2026-08-18 v0.3 で確定・実装済】

**エッジを2種類に分けるのが要**。これをしないと、点いているランプを通り抜けた先まで「通電」になる。

| 種類 | 中身 | 扱い |
|---|---|---|
| 導体エッジ | `wires` ＋ いま閉じている `model.positions[位置]` のペア（スイッチ接点・ヒューズ・カットアウト・巻線） | 抵抗ゼロ＝同電位 |
| 負荷エッジ | `model.kind:"load"` の `pair` ／ `model.kind:"lamps"` の `lamps[]` | ここで電圧が落ちる |

- **導体エッジだけで連結成分に切る**（＝同じ成分は同じ電位）。電源は `kind:"battery"` の `pos`、アースは `kind:"ground"` の端子＝**どちらもデータから見つける**（ノードIDをJSに直書きしない）。
- **負荷が働く = 片側が B+ 成分 ∧ 反対側がアース成分**。
- 端子の状態は**4段**。3段（B+/アース/無電）では足りないことが実装で確定した：

| 状態 | 意味 | テスターを当てると |
|---|---|---|
| `hot` | B+ に導体だけで到達 | 約12V・電流を流せる |
| `post` | **負荷の先**＝働いていない負荷を跨いだ向こう側 | **電圧は出るが電流は流れない** |
| `gnd` | アースに導体だけで到達 | 0V |
| `off` | どちらにも通じない（孤立・断線の先） | — |

- `post` の伝播は**働いていない負荷だけを跨ぐ**（働いている負荷の先は電位が落ちているので伝えない）。
- **B+ 成分とアース成分が同一になったら短絡**（`shorted`）＝L2の故障判定にそのまま使える。
- ⚠️**ダイナモの電機子巻線（`STOP` の `51↔−`）は導体扱い**にしている。実際は巻線＝抵抗だが、チャージ灯（数十Ω）に対して十分小さいので L1 では 0Ω と見なす。**これが「キーONでチャージ灯が点く」の成立条件**なので、負荷側に移すと挙動が壊れる。
- ⚠️アースに負荷経由でしか繋がらない成分は `off`（0V）に落としている。導通試験の意味では「アースに繋がっている」だが、L1は電圧しか見ないので区別しない。
- これだけ。電流も電圧降下も持たない（HANDOFF §2-5「L4はやらない」）。

### C-5 期待値テーブルは**持たずに導出する**（L3・UCM-01の要）
測定点の期待値は L1 の到達性から自動的に出る：`hot`＝約12V／`post`＝**電圧は出るが電流は流れない**（テスターは振れるのに直らない、の正体）／`gnd`＝0V／`off`＝—。
**authoredで書くのは物理が要る例外だけ**（例: 走行中のオルタB+＝13.8〜14.5V、ダイナモ車は挙動が別）。
→ HANDOFF §3 の「期待値も仕様パッチで書き換わる」が、**パッチでグラフが変われば期待値も自動で変わる**という形で自然に満たされる。表を二重管理しない。

## §D 仕様パッチ

```json
{
  "id": "gen-alt",
  "label": "オルタネーター換装",
  "sys": [11],
  "when": { "generator": "オルタネーター" },
  "ops": [
    { "op":"removePart", "id":"regulator" },
    { "op":"removeWire", "id":["w11-02","w11-03"] },
    { "op":"addPart", "part": { "id":"alternator", "terms":["B+","D+"], "model":{"kind":"alternator"} } },
    { "op":"addWire", "wire": { "a":"alternator.B+", "b":"starter.+", "v":"inf" } }
  ],
  "ledger": "出典: （施工実例の典拠をここに書く。terminals_ledger の流儀）",
  "types": "FLRD"
}
```
- `when` は**DB列の値そのまま**（§DB実勢調査で確定した `generator`/`ignition_type`/`fuel_pump` の実値）＝ HANDOFF §2-3「登録データを自動適用・手数ゼロ」がマッピング表なしで成立。
- **op は5種で足りる**: `removePart`/`addPart`/`removeWire`/`addWire`/`setModel`。自由描画は入れない（HANDOFF §6-1）。
- 該当パッチ無し → **その系統だけ純正表示＋注記**（§2-6）。パッチは系統単位で当たるので、他系統は自分仕様のまま。

### §G-2 段取り2で決着した宿題（負荷の先）

段取り1が持ち越した「純粋な到達性だと負荷を通り抜けた先まで B+ になる」問題は、**端子の状態を4段にする**ことで決着（定義は §C-4）。**L4（電圧計算）をやらない方針は一切変えていない**＝グラフの成分を数え直しただけ。

**この段が要る理由は画面で確認できる**: エンジン回転中に「レギュレータのカットアウトが閉じない」故障を入れると、`regulator.51`・`dynamo.51`・`quadro.51` の3点が `post`（負荷の先）になり、チャージ灯は消えたまま。**テスターを当てれば電圧は出るのに灯が点かない**＝球切れかレギュレータか迷う実際の場面がそのまま出る。3段（B+/アース/無電）だとこの3点が B+ と同じ色になり、**診断ツールとして逆に人を誤らせる**。

### §G-3 段取り2で新しく見えた宿題

1. **通電の色と原典の配線色がぶつかる**。原典の線は ROSSO（赤）・VERDE（緑）で描かれていて、いま端子の状態にも赤（B+）を使っている。点だけなら判別できるが、**段取り4で「線が光る」ようにすると、その色が配線色なのか通電状態なのか分からなくなる**。⚠️**段取り4に入る前に決める**（候補: 通電は太さ・輝きで表して色は原典色のまま／通電中だけ状態色に塗り替える）
2. **画面の作りで分かったこと（公開版の設計にそのまま効く）**。最初に作った版は操作パネルと図が縦に並んでいて、**操作すると図が画面外に出て変化を追えなかった**（ユーザー指摘）。直した内容＝①操作は図の直上に `position:sticky` で貼る・長い説明は図の**下**へ ②**図を `<img>` と重ねるのをやめて SVG の中に `<image>` として取り込み**、`viewBox` を動かすだけで図と端子が一緒に拡大するようにした ③**変わった端子のまわりに自動で寄る**（375px に図の全体を出すと端子番号が読めない＝A4縦の配線図をスマホで見せる以上、寄せる仕組みは必須） ④場面ごとに**「見てほしい端子」を持たせて寄り先にする**（変わった端子だけだと図全体に散って寄る意味が無くなる）。⚠️**線が光るようになっても同じ問題が出る**＝段取り4でも「どこを見ればいいか」を先に決めてから描く
