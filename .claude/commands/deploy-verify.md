# デプロイ後の本番確認

直近の git push 後、Cloudflare Pages のデプロイ完了を確認し、変更されたページが本番で正常に表示されているかを検証して報告する。

**ガードレール（必ず守る）:**
- このスキルは**検証・報告のみ**。問題を見つけても勝手に修正・再pushしない（対応案の提示止まり）。
- 反映待ちのリトライは**最大3回（60秒間隔）まで**。それを超えたら「まだ反映されていない可能性が高い。数分後に再実行してください」と報告して**終了する**。無限に待たない。
- 本番HTMLの全文Readは禁止。`curl | grep` で必要な文字列だけ確認する。

## ステップ1: 直近の push 内容を把握

- `git log origin/main -1 --format='%H%n%s%n%ci'` で直近push済みコミットのハッシュ・件名・日時
- `git diff --name-only origin/main~1 origin/main` で変更ファイル一覧
- `*.html` の変更を確認対象リストとする（HTML変更ゼロなら「表示確認対象なし」と報告して終了）

## ステップ2: デプロイ反映の実体確認（最も確実な方法）

`last-modified` ヘッダは当てにならないため、**変更内容そのものが本番に出ているか**で判定する：

1. ステップ1の diff から、追加・変更された**特徴的な文字列**（新しい見出し・属性値など、他と紛れないもの）を1つ選ぶ
2. `curl -s https://www.registro500.com/<変更ページのパス> | grep -c '<その文字列>'` で存在確認
3. 見つからなければ60秒待って再試行（前述のとおり最大3回）

## ステップ3: 変更ページのHTTP応答確認

各変更HTMLについて：

- `curl -s -o /dev/null -w "%{http_code}" https://www.registro500.com/<path>` で確認
- 判定基準: `200`/`301` = 正常、`404`/`5xx` = エラーとして報告対象

## ステップ4: 表示確認（Playwright）

コスト削減のため **site-checker サブエージェントへの委譲を第一選択**とする。確認内容：

- 各変更ページのスナップショット取得
- コンソールエラー（`browser_console_messages`）の有無
- **表示崩れの判定基準**: `<title>` が空／メインコンテンツ領域が描画されない／コンソールに赤エラーがある、のいずれかに該当したら「要対応」

## ステップ5: レポート（この形式で）

- ✅ 正常表示ページ（一覧）
- ⚠️ 問題ページ（症状＋判定根拠＋対応案。**修正はしない**）
- コンソールエラー一覧（あれば）

公開ページの新規追加・URL変更があった場合のみ、`/seo-check` の実行を提案する。
